分析端点提供与控制台相同的汇总数据：组织整体概览、邮件送达状况、预热进度、各营销活动表现（包括每日和每小时明细，以及并排比较）、邮箱健康状况和账户用量。审计端点返回组织的活动记录，即谁在何时、从哪里做了什么。所有端点均为只读。

所有分析路由共用一套身份验证要求：**权限范围** `READ_ANALYTICS` · **组织权限** `view_analytics`。审计路由使用相同的组织权限，但有独立的 API 权限范围。权限范围参考见[权限](/api/permissions/)，凭据传入方式见[身份验证](/api/authentication/)。

除非另有说明，日期按 `YYYY-MM-DD` 解析。错误采用[错误码](/api/error-codes/)中说明的标准 `{error, message, code, request_id}` 封装。

## 获取控制台分析数据 [#get-dashboard-analytics]

`GET /analytics/dashboard`

返回当前组织的主仪表板概览，包括汇总统计、近期活动、表现最佳的营销活动、邮箱健康状况和每日趋势序列。发送和互动总数只统计邮件步骤，已完成的等待和操作步骤不会使这些数字增加。邮箱健康分组互斥，并使用当前连接、同步或预热信誉状态中最严重的一项。身份验证：**权限范围** `READ_ANALYTICS` · **组织权限** `view_analytics`。

| 参数 | 位置 | 类型 | 说明 |
| --- | --- | --- | --- |
| `period` | query | string | 取值为 `7d`、`30d`、`90d` 之一，按包含今天的 UTC 自然日计算。默认 `7d`；其他值均回退为 `7d`。 |
| `campaign_ids` | query | string | 可选。以逗号分隔营销活动 ID，或重复传入此参数，将营销活动相关部分限定到这些活动。最多 `100` 个。 |
| `folder_ids` | query | string | 可选。以逗号分隔营销活动文件夹 ID。每个文件夹表示请求时其中的所有营销活动。最多 `100` 个。 |

### 按营销活动或文件夹筛选 [#filtering-by-campaign-or-folder]

未提供 `campaign_ids` 和 `folder_ids` 时，仪表板覆盖工作区的所有营销活动。提供任一参数时，服务器会将它们解析为一个集合：明确指定的营销活动，加上当前位于指定文件夹中的所有营销活动。通过两种方式重复指定，或同时位于两个指定文件夹中的营销活动，只统计一次。

筛选会缩小所有基于营销活动发件计算的内容：`overall_stats`（发送、打开、点击、回复、退信、相应比率及 `active_campaigns`）、`daily_trend`、`top_campaigns` 和 `recent_activity`。它不会缩小描述工作区邮箱的 `account_health`、`overall_stats.active_accounts` 或 `capacity_today`，也不会影响不属于任何营销活动的[直接发送邮件](/guides/analytics/#direct-mail)。

不属于当前组织或已不存在的 ID 会被丢弃，绝不会扩大筛选范围：如果指定项均不属于工作区，所有营销活动指标都为零。ID 格式错误，或任一类超过 `100` 个，返回 `400`。经过筛选的响应会在 `scope` 中回显本次计算范围：

```json
{
  "scope": {
    "campaigns": [{ "id": "b1f2c3d4-0000-0000-0000-000000000001", "name": "Client A - Dentists" }],
    "folders": [{ "id": "f01d0000-0000-0000-0000-000000000004", "name": "Client A" }],
    "campaign_count": 6
  }
}
```

`campaigns` 和 `folders` 列出请求项中属于该工作区的部分；`campaign_count` 表示它们合计覆盖的不重复营销活动数。未筛选的请求不会返回 `scope`。

## 获取邮件送达能力看板 [#get-deliverability-dashboard]

`GET /analytics/deliverability`

返回组织在指定时间窗口内的邮件送达状况：退信、垃圾邮件投诉、打开、点击和回复的数量及比率，禁止发送和死信积压情况，回复意图分布，种子邮箱投递位置（整体及按收件服务商划分），从预热推导出的各收件邮件托管服务商投递位置，整体健康等级及 `0-100` 综合评分（均基于文档所述阈值），每日时间序列，以及按邮箱和营销活动划分的明细。需要组织上下文。身份验证：**权限范围** `READ_ANALYTICS` · **组织权限** `view_analytics`。

| 参数 | 位置 | 类型 | 说明 |
| --- | --- | --- | --- |
| `from` | query | string | 时间窗口起点，RFC 3339 时间戳。默认为七天前，采用 UTC。 |
| `to` | query | string | 时间窗口终点，RFC 3339 时间戳。默认为当前时间，采用 UTC。 |

## 获取邮箱预热分析数据 [#get-warmup-analytics]

`GET /analytics/warmup`

返回日期范围内的预热发送和回复统计，包含摘要及每日序列。可选择限定为单个邮箱。身份验证：**权限范围** `READ_ANALYTICS` · **组织权限** `view_analytics`。

结果限定在所选工作区，因此所有有权限的成员都会看到相同的邮箱历史。工作区整体结果将所有邮箱汇总为每日一行。`average_daily` 以活跃天数，即存在预热统计记录的日期数为分母。`target_progress` 为这些活跃日的总发送量除以计划目标总量；发送超过计划时可能大于 `100`。

`total_received` 和每日 `emails_received` 统计从预热池伙伴收到且已验证的预热邮件，按验证时所在的 UTC 日期分桶。某天有收件但没有预热计划时，该日发送量列为零，且不计入 `days_active`。

| 参数 | 位置 | 类型 | 说明 |
| --- | --- | --- | --- |
| `from` | query | string | 必填。范围起始日期（`YYYY-MM-DD`）。 |
| `to` | query | string | 必填。范围结束日期（`YYYY-MM-DD`）。 |
| `email_id` | query | string (uuid) | 可选。限定为一个邮箱账户。无效 UUID 会被忽略。 |

```json
{

    "to": "2026-06-12T00:00:00Z"
  },
  "summary": {

  ]

```

未提供 `email_id` 筛选时，`email_account_id` 为全零 UUID。

## 获取预热邮件投递位置 [#get-warmup-placement]

`GET /analytics/warmup/placement`

返回日期范围内，预热邮件在伙伴邮箱中的到达位置：主收件箱、Gmail 分类标签页（推广、动态、社交或论坛），或垃圾邮件。按 UTC 日期和收件服务商计数；工作区报告还按邮箱划分。需要组织上下文。身份验证：**权限范围** `READ_ANALYTICS` · **组织权限** `view_analytics`。

所有数字均为实测，而非估算：只有收件邮箱自身的同步发现预热邮件并记录其到达文件夹后，才会计为一次投递。`rescued` 统计已要求收件邮箱移回收件箱的垃圾邮件投递；实际移动不会回传确认，因此该指标是请求挽救的数量，而非已验证的完成数量。`unconfirmed` 统计发送完成超过 24 小时、但尚无收件方报告发现的邮件，按发送日期分桶；服务商筛选无法拆分此项，因此仅在未筛选时报告。

`rate` 是控制台在每个邮箱旁显示的主要送达指标：`inbox_rate` 为最近 7 个 UTC 日中，到达收件箱或分类标签页的邮件占已投递邮件的比例；在投递样本达到 `min_sample`（`20`）之前，保持为 `null`。`scope` 始终为 `major`：该比率只统计 Google、Microsoft 和 Yahoo 收件方，因为这些服务商会依据发件人信誉筛选邮件。若邮箱的预热邮件只到达其他托管服务商，则没有该比率（`delivered` 为 `0`，`band` 为 `none`）。其他托管服务商始终包含在 `summary`、`daily` 和 `providers` 中，`other_delivered` 与 `other_inbox_rate` 表示它们在同一窗口内的对应指标；没有相关投递时分别为 `0` 和 `null`。`band` 在 `90` 及以上为 `good`，从 `80` 起为 `fair`，低于 `80` 为 `poor`，低于最低样本量为 `collecting`，没有投递为 `none`。每日 `rolling_inbox_rate` 是截至该日、同样三个服务商最近七天的比率；每日数量覆盖全部托管服务商，可按服务商筛选以查看单个服务商。比率为保留两位小数的百分比。

收件服务商分组为 `google`（Gmail 和 Google Workspace）、`microsoft`（Outlook.com 和 Microsoft 365）、`yahoo`（Yahoo 和 AOL）及 `other`；每组列出其 `hosts`，其中 `host` 为空表示尚未检测到收件方的邮件托管服务商。

| 参数 | 位置 | 类型 | 说明 |
| --- | --- | --- | --- |
| `from` | query | string | 可选。范围起始日期（`YYYY-MM-DD`）。默认为 `to` 前 29 天。 |
| `to` | query | string | 可选。范围结束日期（`YYYY-MM-DD`）。默认为今天，采用 UTC。 |
| `email_id` | query | string (uuid) | 可选。限定为工作区中的一个邮箱账户。省略则返回工作区报告，并额外包含 `mailboxes`。 |

范围超过 366 天、`from` 晚于 `to`、日期格式错误或 `email_id` 无效时，返回 `400`；`email_id` 不属于工作区时返回 `404`。

## 获取营销活动分析数据 [#get-campaign-analytics]

`GET /analytics/campaigns/:id`

返回单个营销活动的表现摘要，以及各邮件序列步骤的统计，可涵盖活动全部历史，或仅统计某个日期范围内发送的邮件。`total_contacts` 统计已加入活动的潜在客户，`emails_pending` 为这些潜在客户剩余计划执行的邮件步骤发送量。营销活动必须属于所选工作区。身份验证：**权限范围** `READ_ANALYTICS` · **组织权限** `view_analytics`。

| 参数 | 位置 | 类型 | 说明 |
| --- | --- | --- | --- |
| `id` | path | string (uuid) | 营销活动 ID。 |
| `from` | query | string | 可选。统计时段首日（`YYYY-MM-DD`，UTC）。必须同时提供 `to`。 |
| `to` | query | string | 可选。统计时段末日（`YYYY-MM-DD`，UTC），包含当天。必须同时提供 `from`。 |

同时省略 `from` 和 `to` 时，统计营销活动全部历史。仅提供其中一个、日期采用其他格式，或 `from` 晚于 `to`，会返回 `400`，错误码为 `bad_request`。

统计时段按发送批次定义：选择 UTC 时间从 `from` 当日开始至 `to` 当日结束期间发出的邮件，并统计这些邮件产生的所有打开、点击、回复和退信，无论互动何时到达。9 月 5 日发送、9 月 10 日收到回复的邮件，会计入 9 月 1 日至 7 日的时段；8 月发送、9 月 3 日收到回复的邮件则不会计入。这样可确保各比率的分子和分母针对同一批邮件。时段影响 `emails_sent`、打开、点击、回复、正向回复和退信的数量及比率、`interested_leads`、`reply_breakdown`、`steps` 中的每行，以及 `engagement` 中的每个分桶；只要对应邮件在该时段发送，打开或点击就会计入。`total_contacts` 和 `emails_pending` 描述营销活动当前状态，不随统计时段变化。

`date_range` 表示指标覆盖的时段，以首日和末日的 UTC 零点表示：即传入的 `from` 和 `to`；统计全部历史时，则从营销活动首次发送日开始，尚未发送时从创建日开始，一直到今天。

`engagement` 按国家或地区（ISO 代码）、邮件客户端、设备类型（`desktop`、`mobile`、`tablet`）和使用环境对营销活动的人工打开与点击分组，每个分桶统计不重复联系人。`clients` 的键可以是邮件客户端（`Gmail`、`Apple Mail`、`Outlook`）；若在浏览器打开且未识别客户端，则为 `Webmail in <browser>`；若是点击，则为链接打开时使用的浏览器。`surfaces` 结合设备与应用或网页邮箱，取值包括 `mobile_app`、`desktop_app`、`tablet_app`、`webmail`；两者均未知时仅使用设备类型，点击通常属于这种情况，除非请求由邮件应用自身发出；如果由邮箱服务商的图片代理获取邮件、无法判断设备，则为 `hidden`。每个列表只保留最活跃的八项；`key` 为空表示未知。识别国家或地区需要消费者进程安装 GeoLite2 数据库，否则所有相关行均为未知。

`unique_opens`、`opens`、`total_opens` 及所有打开率只统计人工打开。`machine_opens` 单独统计仅由自动抓取程序打开过的步骤，包括没有 UA 的客户端、已知扫描器网络，以及发生在实例自动打开判定窗口内的打开；该窗口从步骤分派到工作节点时开始。这些不计入打开数量。Apple Mail 隐私保护的中继（用户代理仅为 `Mozilla/5.0`），以及 Mac 上的 Mail 与新版 Windows Outlook 共用的简化 WebKit 特征，只有在该窗口内才被计为预取；它们本身不能证明是自动操作。对于曾被机器打开的步骤，之后若发生人工打开，会从 `machine_opens` 移入人工打开计数。`machine_clicks` 统计在某个步骤上只有自动点击的联系人，例如安全网关逐个访问链接；这些不计入只统计人工点击的 `unique_clicks` 或 `total_clicks`。

`replies` 统计人工回复，联系人每回复一个步骤计一次；外出通知和自动回复永远不计入。`positive_replies` 是其中被[回复分类器](/guides/inbox-tagging/)判定为正向的子集；`positive_reply_rate` 是该数量占 `emails_sent` 的百分比，与 `reply_rate` 使用相同分母。`interested_leads` 统计至少有一次正向回复的不重复联系人，因此对两个步骤作出正向回复的潜在客户只计一次。步骤的分类以最新回复为准：先表示有兴趣、后来又回复拒绝的潜在客户，会计入 `negative`。

`reply_breakdown` 按分类拆分同一批回复。`positive`、`neutral`、`negative`、`unsubscribe`（要求停止联系的回复）和 `unclassified`（分类器无法归类，或在启用回复分类之前收到的回复）合计为 `replies`。`out_of_office` 和 `auto_reply` 统计自动应答，不属于人工回复，仅为完整呈现分类而列出。步骤和每日序列对正向回复采用相同计数方式，因此同一时段内可汇总到摘要。

`steps` 按邮件序列顺序列出营销活动的邮件步骤，与步骤列表返回的顺序一致。`position` 是步骤在这些邮件步骤中从 1 开始的序号，即画布以 `Email N` 显示的 `N`。它不是步骤自身的 `position` 字段：操作步骤不参与编号，删除步骤后不会留空号。应通过 `step_id` 将统计行对应到步骤。

`steps` 中每项都包含该步骤自身的比率：`open_rate`、`click_rate`、`reply_rate`、`positive_reply_rate` 和 `bounce_rate` 均以该步骤的 `emails_sent` 为分母，而不是以整个营销活动的发送量为分母，因此即使跟进步骤只触达十分之一的联系人，也能与首次联系作比较。步骤尚未发送任何邮件时，这些比率为 `0`。`machine_opens` 和 `machine_clicks` 遵循与摘要对应字段相同的规则，但范围限定为该步骤。

`daily_usage.warmup_sent` 和 `campaign_sent` 都统计邮箱当天实际完成的发送量，这也是强制执行发送上限所依据的值，因此两者都不会超过当前生效的目标。

三个 `partner_*_7d` 计数表示最近七天内，通过已确认预热发送触达的不重复伙伴：邮箱、其域名及其所属工作区。失败或仍待完成的尝试不计入。如果整周 `partner_organizations_7d` 都为 `1`，表示邮箱只在一个工作区内部预热；对于未连接 Warmbly Cloud 的自托管实例，这是预期情况，其他环境则值得排查。

`received_7d` 和 `senders_7d` 表示同一窗口内的相反方向：已验证到达的预热邮件，以及这些邮件来自的不重复伙伴。只有邮箱自身同步验证的邮件才计入。如果邮箱在发送侧伙伴很多、接收侧很少，说明它收到的邮件少于发出的邮件；预热池会在每次选择收件方时优先考虑它，直到两侧趋于均衡。

## 获取用量概览 [#get-usage-overview]

`GET /analytics/usage`

返回所选工作区的邮箱账户、营销活动和联系人用量计数。`campaigns.emails_sent` 统计请求时段内已发送的邮件步骤，不计入等待和操作步骤。身份验证：**权限范围** `READ_ANALYTICS` · **组织权限** `view_analytics`。

`api` 对象是兼容性占位符。如需真实的 API 密钥请求总数、错误率、延迟和端点明细，请使用 `GET /api-keys/usage/summary` 及 API 密钥分析端点。

| 参数 | 位置 | 类型 | 说明 |
| --- | --- | --- | --- |
| `period` | query | string | `day` 从今天 UTC 00:00 开始统计，`week` 为滚动七天窗口，`month` 为滚动一个月窗口。默认 `day`；其他值回退为 `day`。 |

### 响应 [#response-10]

```json
{
  "user_id": "11111111-0000-0000-0000-000000000007",
  "period": "day",
  "email_accounts": { "total": 12, "active": 11, "in_warmup": 8, "with_errors": 1 },
  "campaigns": { "total": 9, "active": 4, "paused": 2, "draft": 3, "emails_sent": 124 },
  "contacts": { "total": 8200, "subscribed": 8050, "added_today": 120 },
  "api": { "total_calls": 0, "daily_limit": 50000, "top_endpoints": [] }
}
```

## 列出审计日志 [#list-audit-logs]

`GET /audit-logs`

返回调用者当前组织的完整活动记录，即谁在何时、从哪里做了什么。组织始终从会话获取，不接受客户端参数指定，因此一个组织无法读取另一个组织的记录。身份验证：**权限范围** `READ_AUDIT_LOGS` · **组织权限** `view_analytics`。

| 参数 | 位置 | 类型 | 说明 |
| --- | --- | --- | --- |
| `limit` | query | int | 每页数量。默认 `50`；必须在 `10` 至 `200` 之间，否则返回 `400`。 |
| `cursor` | query | string (uuid) | 来自 `pagination.next_cursor` 的不透明游标。无效游标返回 `400`。 |
| `actor_id` | query | string (uuid) | 限定为某个执行操作的成员。 |
| `entity_id` | query | string (uuid) | 限定为某个实体。 |
| `entity_type` | query | string | 按实体类型筛选，例如 `campaign`、`contact`、`email_account`、`api_key`、`webhook`。 |
| `action` | query | string | 按操作筛选，例如 `create`、`update`、`delete`、`send`、`revoke`。 |
| `date` | query | string | 按单日筛选（`YYYY-MM-DD`），扩展为该 UTC 日期的全天。 |
| `start_date` | query | string | 范围起点。RFC 3339 或 `YYYY-MM-DD`。覆盖 `date`。 |
| `end_date` | query | string | 范围终点。RFC 3339 或 `YYYY-MM-DD`。覆盖 `date`。 |

### 响应 [#response-11]

`data` 加 `pagination` 响应封装，使用不透明游标。如果执行操作的用户之后已被删除，`actor` 为 null；`entity_id`、`changes` 和 `metadata` 为空时省略。

```json
{
  "data": [
    {
      "id": "9c9c9c9c-0000-0000-0000-000000000008",
      "org_id": "0a0a0a0a-0000-0000-0000-000000000009",
      "user_id": "11111111-0000-0000-0000-000000000007",
      "actor": {
        "id": "11111111-0000-0000-0000-000000000007",
        "first_name": "Ada",
        "last_name": "Lovelace",
        "email": "ada@yourdomain.com"
      },
      "action_date": "2026-06-12T08:14:00Z",
      "action": "update",
      "entity_type": "campaign",
      "entity_id": "b1f2c3d4-0000-0000-0000-000000000001",
      "ip_address": "203.0.113.10",
```
