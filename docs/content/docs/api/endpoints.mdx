本页是判断 API 密钥可访问和不可访问哪些内容的权威依据。后端的所有路由均属于以下三类之一：

- **支持 API 密钥**：既可使用 JWT（控制台用户），也可使用具有所列权限的 API 密钥。
- **仅支持 JWT**：API 密钥永远无法访问。用于计费、治理、WebSocket 初始化、危险区域中的销毁操作、OAuth 接入流程及管理工具。
- **公开端点**：无需身份验证（带签名验证的 Webhook、健康检查、OAuth 跳转页面）。

端点标注“JWT permission: X / API permission: Y”时，同时支持 JWT 和 API 密钥的身份验证中间件会根据调用者使用的凭据检查相应权限。

仅限访问 [选定资源](/guides/team-roles/#access-scope) 的成员，无论使用何种凭据，都只能访问少量读取路由，且结果仅限于获授权资源：`GET /campaigns`、`/campaigns-overview`、`/campaigns/:id` 及其 `/logs`、`/steps` 和 `/ab-variants`、`GET /analytics/dashboard`（其 `campaign_ids` 和 `folder_ids` 筛选条件必须指向获授权的营销活动和文件夹）、`/analytics/campaigns/compare`、`/analytics/campaigns/:id` 及其 `/daily` 和 `/hourly`、`GET /analytics/accounts` 和 `/analytics/accounts/:id`、`GET /emails` 和 `/emails/:id`，以及统一收件箱读取路由 `GET /unibox`、`/unibox/count`、`/unibox/overview`、`/unibox/thread`、`/unibox/thread/labels`、`/unibox/scheduled` 和 `/unibox/:id`（对这些成员而言，该路由不会将邮件标记为已读）。其自身账户相关路由 `/auth/*`、`/me/*`、`GET /organization`、`/organization/current`、`/organization/switch/:id`、`/invitations`、`GET /subscription`、`/subscription/features`、`GET /timezones` 和 `POST /getaway` 仍可使用。其他所有路由均返回 `403` `member_access_restricted`，未获授权的营销活动或邮箱返回 `404`。API 密钥自身的邮箱允许列表还会叠加生效：密钥只能访问同时出现在两份列表中的邮箱。

下方所有路径均相对于带版本的基础 URL `https://api.warmbly.com/v1`（例如 `/campaigns` 表示 `https://api.warmbly.com/v1/campaigns`）。详见 [版本管理](/api/)。

### 受限响应数据与工作区策略 [#restricted-response-data-and-workspace-policies]

- `GET /organization/current` 返回受限摘要：`total_campaigns` 和 `active_campaigns` 统计获授权营销活动；`total_contacts` 统计这些活动中的去重联系人；`email_accounts` 统计获授权邮箱；`emails_sent_today` 统计同时属于获授权营销活动和获授权邮箱的已确认营销活动发送。`member_count`、`product_description`、`icp_notes` 和 `voice_profile` 会省略。非受限响应保持原有工作区整体结构。
- `GET /analytics/dashboard` 在返回 `scope.campaign_count` 前，会将营销活动和文件夹筛选条件与授权范围取交集。
- `GET /campaigns/:id/logs` 保留分页和营销活动动态，但受限响应使用安全消息及显式选定的元数据。未获邮箱授权范围内的邮箱地址、上限、跨营销活动发送状态、预热健康信息及账户 ID 均被移除。不暴露跟踪域名、原始服务商错误、未知字段或嵌套元数据。仅授予营销活动访问权，并不意味着授予其发件邮箱访问权。
- 对于受限成员，`GET /auth/me` 和 `/unibox/overview` 仅包含应用于可访问邮箱内邮件的分类。非受限成员仍获得工作区分类登记表。收件箱访问基于邮箱：授予共享邮箱访问权，也会开放其中其他营销活动的会话。
- `GET /unibox/thread/labels` 在列出标签之前，会检查所选组织及实际生效的邮箱允许列表中是否存在相应邮件。未知、跨工作区和不可访问的会话均返回相同的 `404`。可访问但没有标签的会话返回空列表。
- `GET /emails` 仅在所选组织及实际生效的邮箱允许列表范围内解析分页游标。超出任一边界的游标不会为分页提供时间戳。

工作区创建和限额申请路由是上述路由级拒绝规则的例外：它们在服务层验证账户或目标工作区的权限。`POST /organization` 对所有成员关系均受限的账户返回 `403` `member_access_restricted`，实例管理员除外。没有成员关系，或至少有一个非受限成员关系的账户，仍受现有创建限制约束。提交或列出 `/organization/:orgId/limit-requests`，以及删除 `/limit-requests/:id`，要求在请求的目标组织中拥有非受限成员关系。切换当前选定工作区无法绕过这些检查。

工作区通知和按资源所有者寻址的实时投递也会检查当前组织成员关系。仅拥有资源并不足以授权接收工作区级事件。受限、已移除和尚未接受邀请的成员不会收到工作区通知，包括持久化动态和延迟邮件/推送投递。个人登录安全通知仍可接收。已打开资源通道的 30 秒刷新上限，参见 [实时授权与撤销](/api/realtime/#channels)。

这些检查在托管和自托管实例上均使用现有授权，无需新增迁移或配置。现有非受限访问行为保持不变。

`/campaigns/:id/leads/:contactId/` 下的 `hold`、`pause` 和 `resume` 调用控制某个联系人在单个营销活动中的流程暂停：外出自动回复会自动写入暂停，成员也可手动写入。联系人保持订阅状态并继续作为潜在客户，因此这既不是退订，也不是禁止发送。两项写入操作均声明完整暂停状态，而非增量更改；替换有效暂停时保留原始开始时间，因此重试会作用于同一记录，两者均不需要 `Idempotency-Key`。参见 [暂停潜在客户](/api/reference/campaigns/#pause-a-lead)。

同一路径下的 `cc` 调用设置每封发给某位潜在客户的邮件都会抄送的联系人。响应携带联系人姓名和地址，因此除营销活动权限范围外，还需要联系人读取权限。`PUT` 发送完整列表，因此重试会得到相同状态，无需 `Idempotency-Key`。参见 [设置潜在客户的抄送地址](/api/reference/campaigns/#set-a-leads-cc)。

`GET /campaigns/:id/forms` 报告此营销活动链接到的表单，以及收件人对表单的操作：发出的个性化链接、谁打开了链接、谁开始填写、谁已提交。参见 [表单指南](/guides/forms/)。

`GET /campaigns/:id/send-plan` 返回今天的发送计划：营销活动预计发送多少封邮件，以及决定数量的每项限制。活跃营销活动的计划在后台计算，并从已保存的快照返回，因此无论活动规模多大，读取都保持快速。`computed_at` 是遍历计算该快照的时间；若此后活动被编辑、启动、停止，或已进入新的额度日期，且正在计算新计划，则 `stale` 为 `true`：当前数字是最近一次有效结果，最新计划会很快跟上。尚无快照的活动（新创建的活动）则在请求时计算。参见 [发送计划指南](/guides/campaigns/#todays-sending-plan)。

`/email-images` 是工作区用于邮件正文的图片库。`POST` 接受 multipart `file` 字段（PNG、JPG、GIF 或 WebP，最大 5 MB），并返回记录及可放入 `<img src>` 的公开 `url`；这些文件大小与营销活动附件共用同一存储配额。`GET` 采用键集分页，最新在前（`?limit=` 为 1 至 100，`?cursor=` 为不透明的 `pagination.next_cursor`）。`DELETE` 先删除存储对象，再删除记录；若存储拒绝删除，则返回 `503`，因此失败调用不会改变任何内容，可安全重试；删除成功后，已发送邮件中的该图片将无法加载。

`GET /contacts/custom-fields` 列出联系人中使用的不同自定义字段键（按频率排序），用于构建个性化字段选择器和导入列映射器。在 `data` 下返回扁平字符串数组，最多 200 个键。

导入由针对同一文件的两个步骤组成：预览解析文件并建议列映射（将标题匹配到现有自定义字段），提交则应用您选定的映射。提交需要更严格的 `BULK_CONTACTS` 权限范围，因为一次调用最多写入 50,000 行。映射问题、不可用的自定义字段名称或缺少 `email` 列，均使整个请求返回 `400`；参见 [联系人](/api/reference/contacts/)。

AI 联系人调研消耗积分（每次运行 2 积分，即使没有发现结果也计费），且仅保存有引用依据的发现。参见 [AI 联系人调研](/guides/ai-contact-research/) 指南。批量端点最多接受 500 个联系人 ID，并在后台逐步处理。

### 统一收件箱 [#unibox]

| POST | `/unibox/reply` | `WRITE_UNIBOX`（提供 `forward_message_id` 时还需 `READ_UNIBOX`） |
| POST | `/unibox/reply/draft` | `READ_UNIBOX` |
| GET | `/unibox/compose/candidates` | `READ_UNIBOX` |

`PATCH /unibox/folder` 将邮件移到 `inbox`、`archive` 或 `trash`。通过 `email_ids` 指定邮件，通过 `thread_ids` 指定会话，也可同时指定，两者各最多 500 项。有会话 ID 时优先使用 `thread_ids`：只移动会话中的部分邮件，会让该会话继续显示，因为只要任一邮件仍位于某处，会话就会显示在那里。随后，移动操作会传递到启用了 `relay_folder_moves`（默认启用）的每个邮箱：在响应返回后尽力将服务商副本归档、移到垃圾箱或放回收件箱；下一次同步不会撤销任一侧的整理操作，因为服务商端位置独立跟踪，只有服务商自身移动邮件时才跟随。`sent`、`drafts` 和 `spam` 是由服务商决定的投递位置，不是用户手动归档邮件的目标，因此以 `400` 拒绝。参见 [整理会话](/guides/unibox/#filing-a-conversation)。

`PATCH /unibox/seen` 接受相同的两种形式：`email_ids` 指定单封邮件，`thread_ids` 指定整个会话。`folder` 则批量处理一个文件夹，不能与前两者组合。按会话标记未读时，仅标记最新收到的邮件（优先选择不在垃圾邮件和垃圾箱中的邮件）；若没有收到的邮件，则标记最新发件副本；其他情况下发件副本保持已读。草稿永不标记为未读。显式 `email_ids` 和 `folder` 批量操作也不会将发件或草稿副本标记为未读。

`GET /unibox` 默认列出所有工作文件夹，排除垃圾邮件、垃圾箱和归档，因此整理后的会话会从所有视图移出，而不仅是收件箱文件夹。传入 `include_archived=true` 可采用“所有邮件”行为，或传入 `folder=archive` 直接读取归档文件夹。

`POST /unibox/snooze` 接受 `thread_id` 指定一个会话，或 `thread_ids` 指定最多 500 个。单个形式仍返回稍后处理记录；批量形式返回 `data`。`DELETE /unibox/snooze?thread_id=` 接受逗号分隔列表。

带有 `forward_message_id` 的 `POST /unibox/reply` 会转发已存储的邮件，涉及披露邮件内容，因此密钥还需 `READ_UNIBOX`；若密钥限定了邮箱范围，还必须允许访问原邮件所属邮箱。参见 [转发邮件](/api/reference/unibox/#forwarding-a-message)。

`POST /unibox/reply/draft` 根据会话、联系人和您的 [写作风格档案](/guides/unibox/#ai-reply-drafts) 返回 AI 回复草稿（绝不发送）。消耗 AI 积分；参见 [AI 积分](/guides/ai-credits/)。

`POST /unibox/compose/draft` 为新邮件返回有依据的 AI 草稿（绝不发送）：收件人联系人记录、往来历史和工作区写作风格档案会作为提示词的上下文，响应包含 `text` 或用于澄清的 `question`，并附上 `grounding` 报告。与回复草稿一样消耗 AI 积分；参见 [AI 积分](/guides/ai-credits/)。

`POST /unibox/compose` 发送全新的外发邮件（非回复）。`body_html` 按原样发送；`body_plain` 留空时，根据它生成纯文本部分，`POST /unibox/reply` 也采用同样行为。省略 `email_account_id`（或传入 `"auto"`）时，后端为第一位收件人选择最合适的邮箱；响应报告 `account_id`、`account_email`、`auto` 和 `picked_reason`。位于工作区禁止发送名单上的收件人会在任务入队前以 `400` 拒绝。`GET /unibox/compose/candidates?to=<address>` 返回针对该收件人评分的所有活跃邮箱（依据会话历史、剩余每日额度、域名身份验证健康状况），以及解析到的联系人和禁止发送状态；参见 [撰写邮件](/guides/unibox/#composing-a-new-email)。

`/unibox/drafts` 端点保存自动保存的撰写草稿，作用域为组织内的调用用户。草稿 ID 由客户端生成，因此 `PUT` 具有幂等性（适合防抖自动保存和重试）；删除不存在的草稿不作任何操作。草稿携带 `body`（纯文本）和 `body_html`（纯文本草稿中为空）；各自最多 100,000 个字符。

`GET /emails/:id/auth-check` 对邮箱发件域名实时执行 SPF/DKIM/DMARC 查询并报告结果，不更改任何内容。`POST /emails/:id/auth-check` 执行相同查询，并为该域名下的所有活跃邮箱记录结论；DNS 修复后正是此操作解除发送限制，因此需要 `WRITE_EMAILS` 而非 `READ_EMAILS`。写入无需 `Idempotency-Key`：结果完全来自公开 DNS，没有请求体，重复执行会收敛到相同结果。参见 [域名身份验证](/guides/deliverability/#domain-authentication)。

`GET /emails/:id/track` 报告邮箱已保存的跟踪域名，以及此部署预期的 `CNAME` 值（`cname_target`，取自其 `TRACKING_DOMAIN`），不执行 DNS 查询。`PATCH /emails/:id/track` 设置域名并解析一次；`POST /emails/:id/track/verify` 重新解析已保存域名并记录结论，使已完成传播的记录开始生效。两项写入均基于公开 DNS，且无请求体，因此无需 `Idempotency-Key`。发送时仅使用已验证域名；在此之前，打开和点击经过共用跟踪主机。参见 [自定义跟踪域名](/guides/mailboxes/#custom-tracking-domain)。

`POST /emails/:id/hold` 阻止邮箱发送营销活动邮件，直到 `POST /emails/:id/release` 将其恢复；预热不受影响，自动休息逻辑也不会解除手动暂停。`release` 还是邮箱自动进入 `resting` 后的手动退出方式。两项操作均无请求体且具有幂等性，因此无需 `Idempotency-Key`。参见 [手动暂停邮箱](/guides/mailboxes/#holding-a-mailbox-yourself)。

`GET /emails/allowance` 报告工作区当前邮箱数量（`used`）、允许持有的数量（`allowance`，无限制时为 `null`）、`remaining`，以及该数量的 `basis`：`fair_use`（套餐每日发送量除以 `sends_per_mailbox`）、`plan`、`override`（已获批申请）、`free` 或 `unlimited`。`pending_request` 是尚在处理的邮箱增额申请（若有）。`remaining` 为 `0` 后，所有连接途径均以 `mailbox_allowance_reached` 拒绝。参见 [邮箱数量额度](/guides/mailboxes/#mailbox-allowance)。

`GET /emails/:id/identity` 报告邮箱服务商允许使用哪些发件地址、当前使用哪个地址，以及签名是导入的还是在此处编写的；不会联系服务商。`POST /emails/:id/identity/refresh` 从服务商重新读取该列表并保存；提供 `import_signature` 时，还会用服务商配置的签名替换已保存签名。系统依据已保存列表验证 `send_as_email` 选择，因此刷新需要 `WRITE_EMAILS` 而非 `READ_EMAILS`；无需 `Idempotency-Key`，因为它精确写入服务商当前提供的信息。仅限 Gmail。参见 [发件身份](/guides/mailboxes/#sending-identity)。

`GET /emails/:id/sync` 除导入状态和额度外，还报告 `skip_folders`（邮箱同步忽略的文件夹）及 `folders`（工作节点上次从服务器列出的文件夹，每项包含 `name` 及其归属的标准 `folder`，INBOX 在前；Gmail 和 Outlook 为空）。`PUT /emails/:id/sync` 接受 `{"skip_folders": [...]}` 并替换列表：使用服务器列出的名称，匹配时忽略大小写，每项涵盖其子文件夹。新设为跳过的文件夹中已存储邮件会被移除，邮箱会重新发送给工作节点，使变更在下一轮处理时生效，响应返回保存后的列表。`INBOX` 以及任何已发送、草稿、垃圾邮件、垃圾箱或归档文件夹均以 `400 invalid_sync_folder` 拒绝；名称超过 `50` 个或邮箱不是 IMAP 时也同样拒绝。请求体描述目标状态，因此无需 `Idempotency-Key`。参见 [不希望同步的文件夹](/guides/mailboxes/#folders-you-do-not-want-synced)。

对于 SMTP/IMAP 邮箱，`PATCH /emails/:id` 接受 `save_to_sent`（boolean）：为 true（默认值）时，工作节点会将每封外发邮件的副本保存到邮箱的“已发送”文件夹。对 Gmail 和 Outlook 邮箱无效，因为其 API 会自行保存副本。参见 [保留已发送邮件副本](/guides/mailboxes/#keeping-a-copy-of-sent-mail)。

对于所有服务商，`PATCH /emails/:id` 还接受 `relay_folder_moves`（boolean，默认为 true）：为 true 时，通过 `PATCH /unibox/folder` 整理会话也会在邮箱中移动会话。参见 [在邮箱中整理邮件](/guides/mailboxes/#filing-in-the-mailbox)。

同一个需要 `WRITE_EMAILS` 的邮箱 PATCH 接受 `test_mode`（`diagnostic`、`off`、`legacy`）、独立的 `test_send_enabled`/`test_receive_enabled`、正数 `shared_daily_limit`/`rolling_recipient_limit`，以及 `send_recovery_resolution`。修复解除绑定 `held_task_id`/`held_reason`，并要求满足以下之一：`authentication_repaired`，附带同一邮箱中时间更新、明确成功的外发 `evidence_task_id`；或 `operator_provider_confirmation`，附带同一邮箱中已明确应用结果的 `evidence_task_id` 和非空 `confirmation_reference`。仅有新的收件箱同步不能作为证据。对于 `held_reason: "unknown"`，显式服务商确认接受 `operator_confirmed_sent`（要求 `message_id`，可选 `provider_msg_id`/`thread_id`）或 `operator_confirmed_not_sent`（不含邮件/会话句柄），同时要求非空 `confirmation_reference` 且不得提供 `evidence_task_id`。这会将经过审计的正常发送结果加入队列，而不是立即重置暂停。消费者进程先对账处理，再重新开放发送准入；其他结果未知的任务仍保持暂停。超时或缺少已发送副本绝不允许自动重试。现有参与状态为 NULL 的邮箱保持旧版行为；新邮箱默认关闭。参见 [发送安全及精确解除要求](/development/send-safety/)。

`DELETE /emails/:id` 先在 Warmbly Cloud 释放邮箱，再删除本地邮箱。已加入预热池的邮箱所保存的凭据会从池中移除；云端托管镜像的认领状态会被释放，使邮箱返回云端工作区并可再次接管。若云端无法确认释放，删除返回 `409 mailbox_cloud_unenroll_failed` 并保留邮箱记录，以便安全重试。Warmbly 会立即尝试将邮箱恢复到工作节点；若失败，工作节点协调器可能在之后恢复。参见 [邮箱](/guides/mailboxes/)。

`GET /unibox` 和 `GET /unibox/thread` 返回邮件预览：每行携带 `snippet`，即单行摘要，而非邮件正文。通过 `GET /unibox/:id` 读取完整邮件，它返回 `body_plain` 及 `body_html`。HTML 在离开 API 前已清理（移除脚本、事件处理程序、嵌入框架及不安全 URL 协议），因此可安全渲染；链接带有 `target="_blank"` 和 `rel="noopener"`。此显示副本也会移除 Warmbly 打开跟踪像素，包括引用历史中的像素，因此渲染不会记录营销活动打开。存储和实际投递的副本仍保留像素。少数无法读取已存储正文的邮件，其 `body_truncated` 为 `true`，此时 `body_plain` 回退到摘要。同一响应还包含完整邮件信封信息（`from`、`to`、`cc`、`bcc`、`ReplyTo`、`date`、`internal_date`、`message_id`、`in_reply_to`、`size`）、所属邮箱（`email_id`）及其标准 `folder`。

`GET /unibox` 还接受 `address=<value>`（匹配发件人或收件人，用于查询“与此人的所有会话”）及 `direction=sent|received`（根据您自己的邮箱地址确定方向）。

`agent-drafts` 端点为 [收件箱智能体](/guides/inbox-agent/) 提供支持：智能体针对收到的真人回复起草建议回复，并保存在此处供审核。`GET` 列出待审核草稿；`approve` 经正常回复流程发送一份草稿（可提供编辑后的 `body`），并可使用 `Idempotency-Key` 安全重试；`discard` 则将其丢弃。只有批准操作会发送邮件。

### 分析与审计 [#analytics-and-audit]

| 方法 | 路径 | API 权限 |
|--------|------|----------------|
| GET | `/analytics/*`（dashboard、direct、inbox-tagging、deliverability、warmup、warmup/placement、campaigns、accounts、usage） | `READ_ANALYTICS` |
| GET | `/audit-logs` | `READ_AUDIT_LOGS` |

分析读取对 JWT 调用者使用所选工作区，对 API 密钥调用者使用密钥所属工作区。预热及用量总数也遵循此规则，因此无论哪位成员连接邮箱或创建活动，团队成员看到的都是同一工作区历史。

`GET /analytics/warmup` 和 `GET /analytics/warmup/placement` 除本地预热历史外，还包含已关联自托管实例中已加入云端预热池邮箱的详细 Cloud 预热报告。可选 `email_id` 始终是本地邮箱 ID；工作区报告仅请求该工作区已加入预热池的邮箱。Cloud 失败以错误返回，而非空报告或部分报告。每日预热统计包含 `active`，表示该日期是否有预热计划，因此合并来源时，每个活跃 UTC 日期只计数一次。

Cloud 提供 `POST /pool-link/instance/analytics/warmup` 和 `POST /pool-link/instance/analytics/warmup/placement`，仅供实例令牌使用，不接受 API 密钥。两者均接受 `{ "remote_ids": ["uuid"], "from": "YYYY-MM-DD", "to": "YYYY-MM-DD" }`，包含 1 至 100 个已加入预热池的远端 ID，以及最多 366 个 UTC 日期（含首尾）。范围或批量大小无效时返回 `400`；任一 ID 未由调用实例加入时，整个请求以 `pool_link_mailbox_not_found` 拒绝。第一个端点返回每日计数，包括 `active`；第二个返回带有实例侧远端 ID 的原始 `daily`、`hosts`、`sent`、`unconfirmed` 和 `windows` 计数。每日投递位置包含计算滚动比例所需的 `from` 之前回溯数据；托管服务商和发送计数覆盖请求范围，窗口数据则覆盖当前向前回溯的时间窗口。

`GET /analytics/inbox-tagging` 接受 `limit`、不透明的 `cursor` 及 `needs_review` 查询参数，返回 `data`、汇总 `summary` 和 `pagination`。每行携带 `actions`，列出该判定被允许执行的操作（`hold`、`stop`、`task`、`suppress`），`summary.acted` 统计实际执行过操作的行数。`return_date`（`YYYY-MM-DD` 或 `null`）是要求模型确认的外出返回日期，模型答案位于 `answers.return_date`。游标、条数或布尔值无效时返回 `400`。

`GET /analytics/accounts` 以标准 `data` 加 `pagination` 分页结构返回账户健康和用量，使用不透明 `cursor`。传入 `email_ids`（逗号分隔，最多 200 个）可仅请求当前页面显示的邮箱；或使用 `limit`（`1`–`1000`，默认 `1000`）和 `cursor` 遍历完整邮箱清单。每页中的单邮箱读取按批处理，因此单页开销不会随总邮箱数量增长；工作区邮箱超过一页时，可通过 `next_cursor` 访问剩余邮箱，而不会被静默丢弃。游标、条数或 ID 无效时返回 `400`。

| 方法 | 路径 | API 权限 |

`DELETE /api-keys/:id/permanent` 删除已撤销或已过期的密钥，同时删除其使用日志。仍可用于身份验证的密钥返回 `409`，因为撤销操作负责记录凭据何时、为何终止。参见 [撤销与删除密钥](/api/authentication/)。

通过已登录会话调用 `POST /api-keys` 时，要求近期确认（`POST /auth/reauth`），因为密钥的有效期可能长于创建它的会话，被盗浏览器令牌不应能够留下长期凭据。API 密钥调用不受影响：它没有会话，也无法提供第二因素；它自身已由确认过的会话签发，并由 `API_KEYS` 权限范围显式授权管理。因此自动化和 CLI 仍可正常使用。

创建、编辑、撤销和删除密钥仅允许已登录成员或 API 密钥执行；OAuth 应用令牌返回 `403` `oauth_token_not_allowed`。新建或编辑的密钥始终受创建者边界限制：成员不能赋予角色未覆盖的权限，API 密钥也不能赋予调用密钥本身没有的权限、邮箱或 IP 地址（`403` `api_key_permissions_exceed_caller`）。参见 [角色可委派的权限](/api/permissions/#what-a-role-can-delegate)。`GET /api-keys/permissions` 通过 `grantable` 报告调用者的边界。

`DELETE /api-keys/self` 撤销本次请求所使用的密钥，是这里唯一不要求权限范围的路由。凭据必须始终能够终止自身：如果退出要求 `API_KEYS`，用户归还笔记本电脑时，设备上的只读密钥可能仍有效，而 [`warmbly auth logout`](/api/cli/) 正是为防止这种情况。JWT 调用者会收到 `400`：该请求中没有可终止的密钥，只有会话，会话通过 `POST /auth/logout` 结束。

### 重试安全性 [#retry-safety]

更改数据的 API 请求可包含 `Idempotency-Key` 请求头。Warmbly 按组织和幂等键保存已完成响应 24 小时。对相同方法、路由、查询及请求体复用同一幂等键时，重放原始响应，并带有 `X-Idempotent-Replayed: true`；将同一键用于不同请求时，返回 `409 Conflict`。

## 仅支持 JWT [#jwt-only]

这些端点永远不接受 API 密钥。它们依赖绑定到真人的会话：计费流程、治理、OAuth 接入、WebSocket 初始化及运维销毁操作。

采用 [多个控制台共用后端](/development/configuration/#google-sign-in-per-dashboard-deployment) 时，密码重置和邀请邮件、推荐链接及计费返回地址使用发起浏览器所对应的、已明确配置的控制台源地址。没有可信源时，使用主控制台。邮箱、管理员授权、集成和 Slack 身份 OAuth 回调从仍有效的服务端状态恢复目标，绝不使用回调查询参数。已过期或已消费的路由状态不会被转发到其他控制台。

- `POST /auth/login`, `/auth/login/confirm`, `/auth/register`, `/auth/register/confirm`, `/auth/refresh`, `/auth/reset-password`, `/auth/reset-password/confirm`
- `POST /auth/reauth`（对仍有效的会话重新验证账户持有人，用于需要近期确认的更改）
- `GET /auth/reauth/methods`（此账户可用的确认方式：密码、双重验证代码、通行密钥，以及可重新验证的关联登录服务商）
- `POST /auth/reauth/passkey/begin`、`/auth/reauth/passkey/finish`（使用此账户自己的某个通行密钥确认）
- `POST /auth/reauth/sso/begin`、`/auth/reauth/sso/finish`（在浏览器窗口中通过关联到此账户的 Google、Apple 或单点登录身份确认）
- `POST /auth/reauth/native/begin`、`/auth/reauth/native`（使用携带会话 nonce 的原生“通过 Apple 登录”或 Google ID 令牌确认）
- `GET /auth/config`（公开部署能力：后端启用了哪些登录方式、之后是否有登录验证码步骤、注册是否开放、实例是否仍待认领）
- `POST /auth/app-attest/challenge`、`/auth/app-attest/keys`（原生应用的 [App Attest](/api/reference/account-org/#app-attest-native-apps) 质询和一次性密钥注册，采用独立的每 IP 额度 `APP_ATTEST_IP_RATE_LIMIT`）
- `GET /auth/instance`（仅限 JWT：自托管实例当前运行的 Warmbly 版本，以及是否存在更新版本，供控制台版本标记使用；托管部署仅返回 `self_hosted: false`）

`POST /auth/register` 接受可选 `invite` 字段，携带邀请令牌。在采用 `DISABLE_REGISTRATION=invite_only` 的部署中，此令牌用于许可注册，账户会在发出邀请的组织中创建，而不是新建组织。令牌必须对应有效邀请，且邀请邮箱与提交地址相同，否则请求以 `invitation_invalid` 拒绝。在关闭注册的部署中省略此字段，会返回 `registration_invite_only` 或 `registration_closed`。参见 [错误码](/api/error-codes/#registration-and-invitation-refusals)。

### 需要近期再次确认身份的操作 [#actions-that-need-a-recent-confirmation]

以下更改除原有所需权限外，还要求会话在最近五分钟内确认过账户持有人：

| 操作 | 路由 |
|--------|-------|
| 创建 API 密钥 | `POST /api-keys` |
| 在 OAuth 同意页面批准应用 | `POST /oauth/authorize` |
| 批准 CLI 登录 | `POST /auth/cli/codes/:code/approve` |
| 添加通行密钥 | `POST /auth/passkey/register/begin`, `/finish` |
| 移除通行密钥 | `DELETE /auth/passkey/credentials/:id` |
| 启用双重身份验证 | `POST /auth/2fa/enroll/start`、`/confirm`（无密码账户见下方说明） |
| 转移工作区 | `POST /organization/transfer-ownership` |
| 邀请成员、更改成员角色或访问范围 | `POST /organization/members/invite`, `PATCH /organization/members/:id`, `PUT /organization/members/:id/access` |
| 导出或导入整个工作区 | `POST /organization/current/export`, `POST /organization/current/import` |
| 计划删除工作区或账户 | `POST /organization/current/danger-zone/delete`, `POST /me/danger-zone/delete` |
| 批准自托管实例的预热池关联 | `POST /pool-link/codes/:code/approve` |
| 查看或轮换签名密钥 | `POST /webhooks/:id/rotate-secret`, `GET /integrations/connections/:id/webhook-secret`, `POST /oauth/applications/:id/rotate-secret`, `GET /oauth/applications/:id/webhook-secret`, `POST /oauth/applications/:id/webhook-secret/rotate` |
| 记录、使用或移除整个域的管理员授权 | `POST /emails/grants/google/finish`, `POST /emails/grants/microsoft/finish`, `POST /emails/grants/:id/connect`, `DELETE /emails/grants/:id` |
| 管理面板：签发节点集群加入令牌、授予管理员权限、导出或导入任意工作区 | `POST /admin/fleet/join-token`, `POST /admin/admins/:userId/grant`, `POST /admin/organizations/:id/exports`, `POST /admin/organizations/:id/imports` |

这些操作至少涉及以下情况之一：发放有效期长于创建会话的凭据、披露密钥、更改谁可访问、被操作对象本人无法撤销，或访问整个域的邮件。未经确认时返回 `403`，错误码为 `reauth_required`；请确认后重试。参见 [错误码](/api/error-codes/#confirmation-required)。

`GET /auth/reauth/methods` 返回账户可用的确认方式，客户端应只提供这些方式：

```json
{
  "password": false,
  "totp": false,
  "passkey": true,
  "providers": [{ "id": "google", "label": "Google" }],
  "native_providers": ["google"],
  "valid_for_seconds": 300
}
```

- **密码或验证码：** 调用 `POST /auth/reauth`，提供 `password`，或当前双重验证代码或恢复 `code`。
- **通行密钥：** `POST /auth/reauth/passkey/begin` 返回仅限此账户自身通行密钥的 WebAuthn 请求 `options`；将 `options.publicKey` 传给浏览器，再将断言以 `credential` 发送到 `POST /auth/reauth/passkey/finish`。认证器必须验证用户。
- **浏览器中的关联身份：** 向 `POST /auth/reauth/sso/begin` 提供 `provider`（`providers[].id` 之一），返回 `url` 和 `binding`。在窗口中打开 `url`，并保留 `binding`。服务商会将该窗口返回控制台的 `/reauth/complete`，附带一次性 `code`，只有发起流程的会话可以兑换：调用 `POST /auth/reauth/sso/finish`，提供 `code` 和 `binding`。服务商验证的身份必须已关联到该账户；其他账户以 `reauth_identity_mismatch` 拒绝，绝不会按邮箱地址匹配。
- **原生应用：** `POST /auth/reauth/native/begin` 返回 `nonce`。将其原样用作“通过 Apple 登录”请求的 nonce，或 Google 授权的 `nonce`，然后将 ID 令牌发送到 `POST /auth/reauth/native`，并提供 `provider`（`apple` 或 `google`）。nonce 仅可使用一次，并绑定到会话。

各方式成功时均返回 `{ "valid_for_seconds": 300 }`，且仅确认发起调用的会话。

此规则适用于会话调用者。API 密钥或 OAuth 令牌没有可供确认的会话，也不是此处针对的威胁，因此直接进入路由的权限检查。

完成登录后的前五分钟视为会话已确认。对于既无密码也未启用双重验证的账户，`POST /auth/reauth` 返回 `400`，错误码为 `reauth_no_factor`；应改用通行密钥或关联身份确认。如果这些方式都没有，则重新登录。

`GET /auth/config` 新增两个字段：`invites_required`（boolean，创建账户需要邀请令牌时为 true）及 `docs_url`（string，部署提供的账户和访问文档链接，供客户端在拒绝消息旁展示）。

`GET /auth/config` 还携带 `websocket_url` 和 `app_url`（均为字符串，实例未配置相应值时各自省略）。它们分别是开发者客户端连接的实时网关，以及客户端将用户引导至的控制台源地址。两者在这里提供，是因为自托管实例的主机布局由运维人员决定，无法通过其他方式发现：[CLI](/api/cli/) 通过读取它们支持 `warmbly events tail` 和 `warmbly browse`。

`POST /getaway` 仅限会话调用，并签发十分钟有效的 WebSocket 票据。其 `url` 仍为直连网关；可选 `proxy_path` 相对于 `/v1` 解析，用于浏览器连接。`GET /realtime/socket/websocket` 使用该票据升级连接，同时保留已配置实时服务的源检查和连接限制。不接受普通访问令牌、API 密钥或 OAuth 令牌。参见 [实时 WebSocket](/api/realtime/)。

此外，`api_url` 是此 API 自身的公开基础地址（供可复制示例指向正确服务器），`brand` 表示部署声明的品牌身份：`name`，以及 `website_url`、`website_label`、`terms_url`、`privacy_url`、`support_email`，未设置时分别省略。未配置任何 `EMAIL_BRAND_*` 的自托管实例仅提供 `name`；客户端应完全不显示链接，而不是替换成自行选择的链接。参见 [配置](/development/configuration/)。

`GET /auth/config` 还携带 `gmail_oauth_connect`（boolean）：是否允许通过 Google 登录连接新的 Gmail 邮箱。`BOX_GOOGLE_CLIENT_ID` 和 `BOX_GOOGLE_CLIENT_SECRET` 均为必需。两者设置后，该能力默认为 `true`；显式设置 `BOX_GOOGLE_OAUTH_CONNECT=false` 或无效值会禁用它。为 `false` 时，应提供应用密码途径（对 Gmail 服务器调用 `POST /emails/onboarding/smtp-imap`），而不是发起最终返回 `mailbox_gmail_oauth_disabled` 的 OAuth 流程。控制台还要求部署本地的 [前端启用设置](/development/configuration/#google-sign-in-per-dashboard-deployment) 才会显示 Google 登录。无论如何，现有通过 Google 登录连接的邮箱均不受影响。

`GET /auth/config` 还携带 `app_attest`（boolean）：服务器是否在 `POST /auth/login`、`/auth/register`、`/auth/reset-password` 和 `/auth/reset-password/confirm` 上接受原生应用的 [App Attest 证明](/api/reference/account-org/#app-attest-native-apps)，以替代 Turnstile 令牌。结合 `captcha` 读取：没有验证码要求时，无需发送任何内容；需要验证码且有 `app_attest` 时，应用发送证明；需要验证码但没有此能力时，应用内无法使用邮箱和密码登录。

`GET /auth/config` 还携带 `billing_enabled`（boolean）。部署使用 `BILLING_PROVIDER=none`（自托管默认值）运行时，它为 `false`：服务端解锁所有功能，因此控制台将工作区显示为自托管而非免费试用，并隐藏计费及推荐页面。仅有 `self_hosted` 并不意味着如此，因为自托管安装仍可运行 Stripe。

  - `POST /emails/imports/:id/cancel`：停止尚未开始的行；已经连接中的行会继续完成
  - `POST /emails/imports/:id/dismiss`：在工作区的 `GET /emails/imports` 中隐藏此导入；若仍在运行，先停止。其行数据和历史保留，`GET /emails/imports/:id` 仍可读取。返回 `204`；重复调用不作更改

`POST /subscription/checkout`、`POST /subscription/portal`、`POST /subscription/cancel`、`POST /subscription/change-plan` 和 `GET /subscription/preview-change` 要求 `MANAGE_BILLING` 组织权限；读取订阅、限制、试用和功能仅需成员身份。`POST /subscription/portal` 要求已有 Stripe 计费客户。没有计费客户的工作区会收到 `400`，错误码为 `bad_request`，消息提示先完成结账；仅有免费或运维人员授予的套餐不会创建计费客户。

### 内部执行与托管授权 [#internal-execution-and-managed-consent]

`POST /api/v1/internal/email-message-map/lookup` 是仅接受节点令牌的邮箱同步读取端点，不属于客户 API 密钥权限范围。JSON 请求体携带 `user_id`、`email_id` 和最多 200 个 `message_ids`（总大小最多 1 MiB）。成功响应为 `200`，包含 `{"mappings": [...]}`；缺失 ID 被省略，空结果为空数组，而非 `404`。每项返回映射携带 `user_id`、`email_id`、`message_id`、`id` 和 `thread_id`。更新后的 IMAP 工作节点每次批量处理一个邮件信封窗口，不跨处理轮次缓存缺失映射。旧工作节点继续使用单邮件 GET 端点。新工作节点仅在批量路由返回 `404` 或 `405` 时回退，并在十分钟后重新检查批量支持，使现有自托管实例在滚动升级期间继续工作。身份验证失败、数据库错误及格式无效的成功响应仍视为失败，不能作为邮件不存在的证据。不更改同步间隔、到达确认或发送授权。

`DELETE /cloud-link/mailboxes/:id` 移除所选工作区的邮箱加入记录。在 Cloud 上，仅接受实例令牌的 `DELETE /pool-link/instance/mailboxes/:remoteId` 会先停止托管邮箱参与诊断发送和接收，再释放关联，同时保留其 Cloud 邮箱、登录和历史。停止失败时保留关联以供重试；解除关联失败不会重新启用参与。非托管加入仍按原行为删除其 Cloud 邮箱。整个实例的 `DELETE /pool-link/instance` 和经工作区授权的实例解绑，在释放关联时保留托管 Cloud 参与状态。这些移除操作天然可重试；远端加入记录不存在时返回 `pool_link_mailbox_not_found`，自托管客户端将其视为已经释放。

`PATCH /cloud-link/mailboxes/:id/participation` 仅用于自托管、仅接受 JWT，并要求 `MANAGE_EMAILS` 和组织所有权。接受类型明确的 `mode`（`diagnostic` 或 `off`）、`send`、`receive` 及可选的正数共用/滚动限制。`receive` 还授权在支持时，对已验证的预热邮件按概率执行移出垃圾邮件、已读、重要标记、加星或旗标操作；不授权回复，也不保证信誉改善。Cloud 通过仅接受实例令牌、限定在调用实例内的 `PATCH /pool-link/instance/mailboxes/:remoteId/participation` 提供对应操作。这些专用路由防止旧 Cloud 静默忽略新增同意字段；没有参与设置的旧状态不构成显式诊断同意。现有原生生命周期路由在启动/恢复时选择诊断发送和接收，在停止时完全关闭并保留历史。参见 [参与设置与发送安全](/development/send-safety/)。

对于由 Warmbly Cloud 预热的邮箱，`PATCH /emails/:id` 通过仅接受实例令牌的 `PATCH /pool-link/instance/mailboxes/:remoteId` 将 `warmup_base`、`warmup_max`、`warmup_increase`、`warmup_reply_rate`、`warmup_start_time`、`warmup_end_time`、`warmup_days` 和 `warmup`（作为暂停或恢复）发送给 Warmbly Cloud，再保存 Cloud 报告的值。仅在 Cloud 应用其部分之后，才在本地写入其余更新，时区也随之一并发送。`test_mode`、`test_send_enabled`、`test_receive_enabled`、`shared_daily_limit` 和 `rolling_recipient_limit` 返回 `409 cloud_warmup_managed`；请使用上方参与设置路由。`POST /emails/:id/warmup/start` 和 `/resume` 在 Cloud 恢复邮箱，`/pause` 在 Cloud 暂停，`/stop` 返回 `409 cloud_warmup_managed`。`GET /cloud-link/mailboxes` 的行携带 `settings_observed_at`，表示本地副本上次与 Cloud 一致的时间。参见 [预热设置](/guides/warmbly-cloud/#warmup-settings) 和 [拒绝原因](/api/error-codes/#warmbly-cloud-warmup-refusals)。

云端托管 OAuth 另提供 `POST /pool-link/instance/oauth/start-correlated`、`POST /pool-link/instance/oauth/finish-correlated` 和 `POST /pool-link/instance/mailboxes/adopt-correlated`，均仅接受实例令牌，并要求 `protocol: 1`。已验证实例的响应会声明 `managed_consent_protocol: 1`。旧版路由保持不变；能力缺失时，不得利用旧副本可能忽略的字段绕过检查。参见 [Cloud 路由与恢复约定](/guides/warmbly-cloud/)。

`POST /internal/worker/warmup-dispatch` 是执行平面内部令牌路由，不属于公开 JWT/API 密钥权限范围。它检查、启动并持久化完成绑定到任务/邮箱/工作节点/nonce 的命令。启动时重新执行权威策略检查；授权未知或被拒绝时，不得执行原生操作。回执、邮件头或模型文本均不提供授权。

`POST /internal/email-message-map/arrival` 使用现有内部节点令牌。只有带有 `X-Warmbly-Arrival-Durable: 1` 的 `204` 才确认已持久化接纳。若权威检查确认所请求的精确邮箱/用户所有权不存在，则返回 `503`，并通过 `X-Warmbly-Arrival-Ownership-Lost` 携带请求的邮箱 UUID，不提供持久化确认。更新后的工作节点仅终止该邮箱这一代实例的处理；失败的到达记录保持未确认，保留已存储正文，且不推进服务商游标。普通 `503` 响应、传输失败、数据库失败和加密失败仍可重试。旧工作节点忽略新标记，继续保留该到达记录；只有后端和工作节点都升级后才能执行此终止处理。这不会清除发送暂停、重发邮件或更改 Kafka 偏移量。

`POST /internal/worker/outbound-dispatch`、`/internal/worker/warmup-actions` 和 `/internal/worker/diagnostic-auth` 使用现有执行平面内部令牌，绝不接受客户 API 密钥。它们绑定当前邮箱/工作节点，并要求协议 2。外发启动还会重新检查任务/组织/服务商/nonce/收件人及当前营销活动或诊断策略。诊断授权和结果提交绑定一个精确、已归属的预热回执及短期 nonce；既不接收无关收件箱邮件，也不信任事件/邮件头声明。未新增任何公开权限范围或权限。详情及限制见 [发送安全](/development/send-safety/)。

对于已删除、未分配或不再获授权的邮箱，预热操作不返回任何允许的动作。工作节点将这种权威拒绝视为无操作，不接触服务商。数据库或授权服务失败仍返回 `503` 并重试；拒绝不会授权发送、清除发送暂停或确认到达。

`POST /internal/worker/warmup-actions` 可接受 `filing_id`，用于仅整理邮件的操作。只有已获许可、仍在持久化队列中、且精确对应该邮箱及当前工作节点的纯整理工作，才返回 `filing_pending: true`。整理失败时，此证明允许更新后的工作节点在没有 `WarmupFiled` 完成事件的情况下结束命令；持久化恢复队列仍负责重试。缺少证明或后端较旧时，保留现有命令重试行为。先部署后端，再部署工作节点以启用此行为。整理成功仍要求完成事件，发布失败仍可重试。没有增加任何发送、到达或按保留策略删除的授权。

### Slack [#slack]

[Slack](/guides/slack/) 面板的路由。仅限会话调用：关联操作将 Slack 账户绑定到已登录用户，而 API 密钥没有可供绑定的用户身份。设置变更和移除关联会发布 `AUDIT_CREATED`，其中 `entity_type` 为 `integration`。

| 方法 | 路径 | JWT 权限 |
|--------|------|----------------|
| GET | `/integrations/slack/status` | 组织成员。所有人可获取 `app_configured`、`interactive_configured` 和 `my_link`（始终为调用者自身的关联）；`connection`、`settings` 和 `missing_scopes` 仅提供给具有 `manage_settings` 或 `use_integrations` 的成员（否则分别省略、为 `{}` 和 `[]`）；`links`（所有成员的关联）仅提供给具有 `manage_settings` 的成员 |
| GET | `/integrations/slack/channels` | `manage_settings` 或 `use_integrations`。返回公开频道及机器人所在的私有频道，按 `q` 筛选，最多 200 项，采用 `data` 加 `pagination` 的结构 |
| PUT | `/integrations/slack/settings` | `manage_settings`。默认 `channel`、按分类的 `routes`、`assistant_disabled`、`assistant_dm_only`、`inbox_channel`（列表中的频道 ID；为空时关闭 [收件箱频道](/guides/slack/#inbox-in-slack)），以及 `inbox_scope`（`replies`，默认值，或 `all`）。收件箱频道必须对机器人可见，且不能是 Slack Connect 频道，否则返回 `400`。具有幂等性：替换整个设置对象 |
| GET | `/integrations/slack/link/:code` | 已登录，可处于任意工作区。预览机器人按钮携带的关联信息：`organization_id`、`organization_name`、`is_member`、`slack_team_id`、`slack_team_name`、`slack_user_id`、`slack_user_name` 和 `slack_user_avatar`（以 Slack 当前报告为准，后两者均可能为空）、`user_email`（调用者 Warmbly 邮箱）、`email_matches`（Slack 账户邮箱是否与调用者 Warmbly 邮箱相同）、`verify_available`（是否可通过 Slack 登录确认关联）及 `expires_at`。未知或过期代码返回 `404` `slack_link_invalid` |
| POST | `/integrations/slack/link/verify` | 已登录，且为代码所属工作区的成员（否则返回 `403` `forbidden`）。提交机器人按钮中的 `code`；以 `200` 返回 `url`，指向代码所属 Slack 工作区的“通过 Slack 登录”页面。Slack 返回集成 OAuth 回调，再将 `code` 和 `state` 传给打开窗口的页面。Slack 应用没有客户端凭据时返回 `503` `slack_verify_unavailable` |
| POST | `/integrations/slack/link` | 已登录，且为代码所属工作区的成员（否则返回 `403` `forbidden`）。提交机器人按钮中的 `code`；调用者 Warmbly 邮箱与代码中 Slack 账户邮箱不同时，还需提供 Slack 登录返回的 `slack_code` 和 `state`（缺少时返回 `403` `slack_link_email_mismatch`，代码仍可继续使用）。Slack 登录结果必须属于此调用者、对应此代码及代码中的 Slack 账户（否则返回 `403` `slack_verify_failed` 或 `slack_verify_wrong_account`）。以 `201` 返回关联，并替换该 Slack 账户先前的关联。代码仅可使用一次，因此重复调用以 `404` `slack_link_invalid` 拒绝 |
| PATCH | `/integrations/slack/link` | 组织成员，自身关联。`dm_notifications`。调用者在此工作区没有关联时返回 `404` `slack_not_linked` |
| DELETE | `/integrations/slack/link` | 组织成员，自身关联。返回 `204`，没有关联时也如此，因此可安全重复调用 |
| DELETE | `/integrations/slack/links/:id` | `manage_settings`。移除任意成员的关联。返回 `204` |

接受代码的两个 `/integrations/slack/link` 路由无需选定工作区，因为代码已指明工作区。`GET /integrations/slack/status` 报告 `app_configured`（实例有 Slack 应用）和 `interactive_configured`（还具有签名密钥，因此助手和按钮可用），使客户端在调用其他接口前了解可用能力。工作区尚未连接 Slack 时，设置和频道路由返回 `404` `slack_not_connected`。错误码见 [404](/api/error-codes/#404-not-found) 和 [503](/api/error-codes/#slack_not_configured)。

## MCP 服务器 [#mcp-server]

`POST /v1/mcp` 通过 [模型上下文协议（Model Context Protocol）](/api/mcp/) 的流式 HTTP 传输提供工具登记表。接受具有 `AI_AGENT` 的 API 密钥或 OAuth 2.1 访问令牌（未认证请求获得 RFC 9728 发现质询）。各工具按自身权限范围控制，`tools/list` 仅反映凭据允许的内容，且永不暴露发送类工具。适用每密钥限流。

## 定时任务 [#scheduled-jobs]

`GET /admin/jobs` 要求管理员权限 `view_analytics`，在 `data` 中返回已注册循环任务及保留的已停用记录。每行包含服务、间隔、最近记录的状态和错误、执行计数器及记录的时间安排。`retired_at` 出现时，表示显式归类为停用的时间戳，不能证明最后一个进程何时停止。停用记录及其历史值仍显示在 Jobs 中；在运行监控中，它们不属于当前运行、逾期、失败或成功的任务。

`POST /admin/jobs/:name/run` 要求管理员权限 `manage_settings`。它请求已注册循环任务在下一次轮询时运行，不直接执行任务本身。不存在和已显式停用的记录返回 `404 not_found`。停用循环不能认领新的计划时段，也不能接收手动请求。停用不会中断已经获准运行的任务，也不会删除其完成证据。

迁移 286 仅将已从应用移除的后端 `fleet_quarantine` 循环归类为停用。其他旧任务或停滞任务仍保持活跃，并保留监控警告。不按任务年龄自动停用。重新注册循环会重新激活记录，并清除旧的待运行请求，但不重置执行计数器或错误。

### 近期诊断证据 [#recent-evidence]

`GET /admin/fleet/nodes/:id/logs` 接受可选 `after`/`before`（含边界的 RFC3339 时间戳，after 不得晚于 before）、`level`（`info`、`warn`、`error`）、`mailbox_id`（邮箱账户 UUID，不是文件夹或邮件）及 `limit`（整数 1..200，默认 200）。结果最新在前，每个节点最多保留一小时和 1,000 个事件；过期或因数量限制淘汰的证据无法恢复。这是允许列表内的进程证据，不是完整日志导出。

响应 `200`（`Cache-Control: no-store`）：

```json
{
  "node_id": "<node UUID>",
  "availability": "fresh", "coverage": "partial",
  "reason": "allowlisted_evidence_only", "observed_at": "2026-10-10T06:10:00Z",
  "capture": {
    "protocol": 1, "run_id": "<process UUID>", "started_at": "2026-10-10T06:00:00Z",
    "observed_at": "2026-10-10T06:09:58Z", "received_at": "2026-10-10T06:09:59Z",
    "dropped": 2
  },
  "events": [{
    "id": "<event UUID>", "observed_at": "2026-10-10T06:09:50Z",
    "event": "sync_control_plane_held", "level": "warn", "category": "control_plane",
    "mailbox_id": "<mailbox account UUID>", "http_status": 503, "count": 1
  }],
  "oldest_retained_at": "2026-10-10T06:09:50Z", "newest_retained_at": "2026-10-10T06:09:50Z",
  "retained_count": 1, "truncated": false, "retention_seconds": 3600, "max_events": 1000
}
```

尚未观测到时省略 `capture`。最早/最新时间及数量描述整个保留窗口，而非筛选后的行。`truncated` 表示响应条数上限之外仍有匹配的保留记录。`dropped` 统计该进程启动后已知的队列溢出/传输重试耗尽批次数，而非整个生命周期的丢失量；在 `run_id` 改变时重置。崩溃丢失、安装采集功能前的事件及丢失的确认无法完整度量：即使接收成功但确认丢失，重试耗尽的批次仍计为丢弃。TTL/数量淘汰属于预期保留策略，而非传输丢失。

| 可用性 / 原因 | 含义 |
| --- | --- |
| `unavailable` / `log_credential_unavailable` | 旧版/手动工作节点，或 Redis 加入状态丢失；请重新加入 |
| `unavailable` / `capture_not_observed` | 已加入，但尚未收到升级后的采集数据；可能是旧工作节点 |
| `unavailable` / `cache_unavailable` | 无法读取历史，不代表错误数为零 |
| `stale` / `no_recent_capture` | 采集观测超过两分钟；仍可能显示保留记录 |
| `fresh` / `no_recent_evidence` | 近期空采集，不能证明服务商健康 |
| `fresh` / `allowlisted_evidence_only` | 新近的部分证据，绝不能据此推断完整覆盖或健康状态 |

固定事件结构：UUID `id`、RFC3339 `observed_at`、允许列表中的 `event`、标准 `level`/`category`、可选邮箱 UUID，以及数值 `count`（0..1,000,000）。仅 `sync_control_plane_held` 保留数值 HTTP 状态（100..599），包括实际同步映射/控制平面的 503 响应。

| 事件 | 类别 / 级别 | 观测到的行为 |
| --- | --- | --- |
| `sync_control_plane_held` | `control_plane` / `warn` | 实际同步控制平面调用失败；中止本轮处理，保持游标不变 |
| `sync_message_deferred` | `control_plane` / `warn` | 未发布映射的清理失败，跳过本轮处理 |
| `mailbox_provider_unreachable` | `provider` / `warn` | 实际同步连接/传输失败 |
| `mailbox_provider_auth_failed` | `provider` / `warn` | 实际同步身份验证/授权失败 |
| `mailbox_provider_throttled` | `provider` / `warn` | 实际同步限流 |
| `mailbox_provider_sync_completed` | `provider` / `info` | 此前传输失败后，观测到一次完整处理成功 |
| `sync_folder_skipped` | `sync_policy` / `info` | 同步策略排除的文件夹数 |
| `sync_message_deferred_by_policy` | `sync_policy` / `info` | 某轮同步中被延后的邮件数 |
| `sync_skipped_folder_search_failed` | `provider` / `warn` | 实际被排除文件夹搜索失败 |
| `sync_legacy_arrival` | `compatibility` / `warn` | 使用了现有旧版到达回退机制 |
| `worker_error` | `worker_runtime` / `error` | 仅工作节点 Zap 错误级别，不包含任意日志文本 |

历史还报告 `generic_error_coverage: "unavailable"` 和 `generic_error_reason: "unhooked_runtime_sources"`。通用运行时错误采集目前仅接入工作节点 Zap。工作节点 Zerolog 和消费者进程 standard-log/Zerolog 错误尚未采集。显式允许列表内的同步/服务商/控制平面决策采集点仍独立存在且保持不变。新近的空采集（包括消费者进程采集）绝不能证明运行时错误为零或系统健康。这些字段描述的是来源覆盖缺失，不是当前故障。

不转发地址、主题、正文、邮件头、原始错误、文件夹名称或服务商凭据。未知自由格式字段被丢弃；类别和级别在传输前，以及接收/读取时重新构建。未知事件被拒绝。证据不会更改同步租约、游标处理、到达接纳或发送授权。

### 节点数据接收 [#node-ingestion]

`POST /api/v1/internal/fleet/nodes/:id/logs` 仅接受加入时签发、专属于该节点的 `Authorization: Bearer <NODE_LOG_TOKEN>`。现有节点集群加入令牌授权在 `env_b64` 中签发此凭据。不接受共用消息代理/内部令牌；哈希精确绑定一个已注册节点，并在接收时进行原子复核。重新加入会轮换凭据；删除节点会撤销凭据并清除日志状态。此凭据仅授予证据提交权限，不授予邮箱或命令访问权限。

不存在用消息代理密钥刷新日志凭据的端点：现有消息代理密钥验证节点集群身份，不证明某个节点 UUID 的所有权。现有节点必须升级，并使用相同 UUID 重新执行已认证的加入流程。常规加入脚本从现有 `node.env` 读取 UUID，保留 `node.local.env` 并重启服务；不要移除配置目录或删除集群节点记录。在收到采集数据前，可用性为不可用，而非健康。Redis 加入哈希丢失时也需要采用相同安全重新加入流程，且不会导入历史日志。参见 [升级顺序与覆盖范围](/development/data-control/#upgrade-order-and-coverage)。

请求 JSON（最多 32 KiB、32 个事件；事件使用上述结构）：

```json
{
  "protocol": 1, "batch_id": "<UUID, stable across retries>", "run_id": "<process UUID>",
  "started_at": "2026-10-10T06:00:00Z", "observed_at": "2026-10-10T06:09:58Z",
  "dropped": 2, "events": []
}
```

空批次仅报告采集覆盖情况。批次时间必须在接收前两分钟内，且不得超前一分钟。事件必须位于一小时保留期内，且不得超前一分钟。`started_at` 必须存在，且不得晚于观测时间。重复批次 ID 在一小时内具有幂等性；旧批次不能覆盖较新的采集元数据。采集周期为五秒，队列容量 256 个事件，最多尝试三次，使用有上限的退避和五秒 HTTP 超时。采集绝不等待网络或队列空间。已认证请求上限为每节点每分钟 30 次。成功返回 `204`；错误采用标准响应结构：`400 bad_request`（协议/时间/边界/事件无效）、`401 unauthorized`（凭据缺失、节点不匹配或已撤销）、`404 not_found`（已注册节点不存在）、`429 rate_limit_exceeded`（`Retry-After: 60`）及 `503 service_unavailable`（依赖问题）。

### 消息代理的已提交消费进度滞后量 [#broker-committed-lag]

`GET /admin/fleet/nodes/:id/broker` 接受已注册工作节点 UUID，不允许覆盖主题或消费者组。现有只读范围保持独立：`commands` 观测 `worker-<UUID>` / `w.<UUID>`；`results` 观测 `consumer-group` / `jobs.worker-events`，这是共用结果，不能归因到该工作节点。不新增消费者权限范围，也不更改偏移量。

响应 `200` 包含 `node_id`、RFC3339 `observed_at`、`commands`、`results` 和 `note`。各部分使用现有 `MonitoringSource`：`id`、`availability`、`coverage`，可选 `reason`、`observed_at`、`checked_at`，已测量/预期范围，以及 `metrics`。成功指标为 `committed_lag`（消息数）和 `members`，包含计数、观测/证据时间戳、`condition: "unknown"`、严重程度及提示说明。仅此专用端点启用滞后分区详情：

```json
{
  "broker": {
    "consumer_group": "worker-<UUID>", "topics": ["w.<UUID>"],
    "partitions": [{"topic":"w.<UUID>","partition":0,"earliest":10,"committed":16,"latest":22,"committed_lag":6}]
  }
}
```

会验证所有请求的主题/分区，以及已提交/最早/最新偏移量；分区 ID 必须非负，每个范围最多 128 个分区，按主题/分区排序。缺少提交、偏移量超出保留范围、分区不匹配、滞后为负或溢出、权限错误和超时均视为不可用，绝不将其截为零。失败指标计数为 null，不含消息代理详情，条件为 unknown，并记录尝试观测的时间。原因包括 `dependency_missing`、`resource_absent`、`permission_denied`、`timeout`、`collection_failed`；非 Kafka 或不支持的消息总线返回 `unsupported` 和空指标。某个范围失败不会隐藏另一个成功范围。整体采集时限为八秒。

滞后 **不** 等同于投递、服务商健康、吞吐量、未提交的在途工作、队列清空时间或故障。仅凭成员数量也不能判定故障。错误：`400 bad_request`（UUID/非工作节点/无效日志筛选）、`401 unauthorized`、`403 admin_mfa_required`/`forbidden`、`404 not_found`、`503 service_unavailable`（节点登记表）。日志 Redis 读取失败则返回 `200`，明确标注覆盖不可用。成功诊断使用 `Cache-Control: no-store`。

## 内部预热恢复 [#internal-warmup-recovery]

这些控制平面端点使用现有节点内部凭据，不使用 API 密钥、控制台 JWT 或节点日志凭据。基础路径为 `/api/v1/internal`，而非上方公开 API 基础路径。不引入新节点身份或凭据交换。

| 方法 | 内部路径 | 权限范围 |
| --- | --- | --- |
| POST | `/worker/warmup-actions` | 检查当前邮箱分配及允许操作；精确匹配的待处理单文件整理工作可返回带版本的整理恢复证明 |
| POST | `/worker/warmup-actions/defer` | 在当前邮箱分配下，为精确匹配的待处理整理操作提交单调不减的服务商重试时间 |

延后操作接受 `mailbox_id`、`worker_id`、`filing_id` 和绝对 `provider_retry_at` 时间戳。仅在提交后才返回成功 `persisted: true`，并提供 `filing_recovery` 证明，包含协议 `1`、相同的三个 ID 及保留的时间戳。请求更短时间绝不会缩短现有服务商暂停或普通重试租约。延后操作没有 GET 变更，也不会产生新的整理成功事件。

对于精确匹配的整理命令，若待处理整理已完成、不存在、归属其他资源或操作载荷不同，升级后的后端不返回任何允许操作。工作节点跳过服务商整理，且不会为此拒绝发出整理成功事件。未跟踪的操作保持现有准入行为。

标识符或时间无效返回 `400`；工作已过时、已删除、归属其他资源或不被允许时返回 `403`；授权能力不受支持或数据库失败返回 `503`。响应使用 `Cache-Control: no-store`。客户端不会接受未标记、格式错误、版本不支持或范围不正确的回复作为持久化延后证明。现有旧后端的重试行为保持不变；旧工作节点不实现服务商重试时间下限。先升级后端及来源实例数据处理说明，参见 [预热重连恢复](/development/data-control/#warmup-reconnect-recovery)。

## 说明 [#notes]

- 当路由同时列出 JWT 权限和 API 权限时，同时支持 JWT 和 API 密钥的身份验证中间件对浏览器调用者检查 JWT 用户的组织角色，对 API 密钥调用者检查密钥权限位掩码。两者是独立检查：除创建时授予的权限外，用户角色不会进一步限制 API 密钥的操作能力。
- 每个 API 密钥请求都记录到 `api_key_usage_logs`，包含端点模式（例如 `/campaigns/:id`）、方法、IP、user-agent、响应状态及耗时毫秒数。JWT 请求不在此处记录。
- 速率限制类别（`X-RateLimit-*` 请求头）按底层用户而非密钥划分；同一用户签发的所有密钥共用该用户的额度。
