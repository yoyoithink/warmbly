## 使用须知 [#good-to-know]

- 每个工作区最初都有**管理员**、**运营者**和**查看者**角色，你可以编辑、删除这些角色，或添加新角色。
- **所有者**是一种成员身份，而非角色；每个工作区恰好有一位所有者。
- 拥有多个角色的成员获得这些角色权限的并集。
- 访问范围限制为**所选资源**的成员仅具有只读访问权限。
- 邀请成员、调整成员角色和移除成员均需要**管理团队**权限。

## 团队设置入口与管理权限 [#where-team-settings-live-and-who-manages-them]

与团队共用工作区：通过电子邮件邀请成员，为每个人分配角色，由角色决定其可以查看和修改的内容。还可以设置访问范围，进一步限制角色适用的营销活动和邮箱，让客户或承包商在你的工作区内协作，同时只能看到指定内容。成员列表和邀请位于**设置 > 成员**；角色和权限矩阵位于**设置 > 角色与访问权限**。

<Callout type="info" title="谁可以管理团队">
邀请成员、调整角色、移除成员和管理角色均需要**管理团队**权限。所有者和预设的管理员角色具有此权限，自定义角色也可以包含此权限。没有此权限时，成员列表只能查看。
</Callout>

</Fold>

## 邀请成员 [#inviting-members]

在**邀请团队成员**框内，将地址粘贴或输入到**电子邮件**字段，以逗号、分号、空格或回车分隔。每个地址会变成一个标签：有效地址为灰色，格式有误的地址为红色，便于先将其移除。为这批成员选择一个或多个**角色**，右侧说明会显示将授予的权限；也可以缩小这批成员的**访问范围**（参见[访问范围](#access-scope)），然后点击**发送邀请**。受限的受邀者从加入的那一刻起就受到限制，不会出现可以短暂查看整个工作区的情况。

Warmbly 向每个地址发送一封邀请，并以“已邀请 2 人 · 1 人失败”的形式报告结果。无效地址会被跳过并单独提示。批量邀请完成后，地址标签会清空。

多个受信任的控制台共用同一个后端时，邀请邮件中的链接会指向发出邀请的控制台。复制邀请链接时，也会保留该控制台的主机名。参见[多控制台配置](/development/configuration/#google-sign-in-per-dashboard-deployment)。

**待接受的邀请**显示每份尚未接受的邀请对应的电子邮件地址、角色、访问范围和到期时间。每行右侧有两个操作：复制邀请链接，以便直接分享，无需等待邮件；以及取消邀请。这里没有重新发送按钮。要向某人提供新链接，请再次邀请同一地址：现有邀请会被替换，生成新令牌并重置到期时间，之前通过邮件发送和复制的链接都会失效。再次复制链接也会签发新链接，因此只有最近一次复制的链接有效；邮件中的链接不受此次复制操作影响。

<Callout type="info" title="角色可以随时调整">
邀请时分配的角色以后可以直接在成员列表中修改。因此，可以先授予较少的权限，再根据需要扩大访问范围。
</Callout>

### 在自托管实例中 [#on-a-self-hosted-instance]

自行托管 Warmbly 时，有两点不同。

**受邀者通过邀请链接创建账户。** 自托管实例默认不开放公众注册（`DISABLE_REGISTRATION=invite_only`），因此直接访问注册表单会遭到拒绝。邀请链接携带允许注册的令牌，所以受邀者可以完成注册：打开链接，点击**创建账户**，随后进入你的工作区，而不是新建的工作区。

**邀请可能不会通过邮件送达。** 平台邮件默认使用将消息写入后端日志的传输方式，不会真正投递。因此，复制邀请链接是常规邀请方式，而非备用方案。当服务器报告不投递邮件时，成员页面会在**电子邮件**字段上方显示琥珀色提示，说明应先邀请此人，再从**待接受的邀请**中对应的行复制链接。

[账户与访问](/development/accounts-and-access/#without-a-mail-relay)介绍了这两种情况，以及如何将实例连接到实际的邮件中继服务。

</Fold>

## 成员名单 [#the-roster]

每行显示电子邮件地址、角色、访问范围和加入日期，你自己的行会标记“你”。打开某行的角色选择器，可以勾选该成员拥有的角色；成员可以拥有多个角色，实际权限是这些角色权限的并集。所有者所在行显示固定的“所有者”标记；你不能编辑自己的行。

要移除成员，请将鼠标悬停在其所在行，或点按该行，然后点击移除图标。**不能移除所有者或你自己。** 如果要离开你拥有的工作区，请先转移所有权。

移除操作也会对当前已登录的成员生效。其已打开的控制台会在下一次请求时失去对该工作区的访问权限，实时更新随之停止，并提示其选择自己所属的其他工作区。该成员在工作区内授权的应用会断开连接。该成员创建的内容不会随其移除：邮箱、联系人、营销活动和 API 密钥都属于工作区；如果也需要撤销其密钥，请到 **API 密钥**中操作。实时通道至少每 30 秒刷新一次访问权限，而且在授权检查已过期时会先重新检查，再投递数据，即使错过了权限变更事件也不例外。角色或所有者变更会直接影响已打开控制台的实时更新，无需重新加载页面。

</Fold>

## 访问范围 [#access-scope]

角色决定成员可以执行哪些操作，访问范围决定这些权限适用于哪些资源：

- **整个工作区**：默认选项，也是引入访问范围功能之前所有成员的访问方式。
- **所选资源**：只能访问你选择的营销活动文件夹、营销活动和邮箱。

点击成员所在行的**访问范围**单元格即可修改。在对话框中选择**所选资源**，再从以下三个列表中选择：

| 授权对象 | 授予的访问权限 |
| --- | --- |
| **营销活动文件夹** | 每次请求时，该文件夹内的所有营销活动。将营销活动移入文件夹即授予访问权限，移出则收回权限。 |
| **营销活动** | 单个营销活动，适合不按文件夹组织营销活动的工作区。 |
| **邮箱** | 统一收件箱中属于该邮箱的会话。 |

只要营销活动位于至少一个已授权的文件夹中，或被单独授权，成员就可以访问它。营销活动的访问权限不会包含任何邮箱，甚至不包含该活动用于发送邮件的邮箱：收件箱访问始终需要逐个邮箱授权。邮箱选择器下方的**所选营销活动的发件邮箱**列出所选营销活动和文件夹使用的发件邮箱，便于检查并一键添加。受限成员如果没有选中任何资源，就无法访问任何资源。

<Callout type="warn" title="共享邮箱会开放其中会话的访问权限">
收件箱访问权限按邮箱授予。若授权的邮箱也供其他营销活动使用，该邮箱中属于那些活动的会话同样会向成员开放，即使没有授权这些营销活动本身。授权邮箱前，请先确认它的使用情况。
</Callout>

<Callout type="warn" title="受限访问为只读">
受限成员的角色仍然适用，但只有读取权限生效：**查看营销活动**、**查看分析数据**和**使用统一收件箱**（仅限读取）。在访问范围受限期间，其余权限均暂停生效，因此成员不能编辑、启动、发送、回复、添加标签、移动内容，或将任何内容标记为已读或未读。打开会话也不会将其标记为对团队其他成员而言的已读状态。
</Callout>

受限成员可以看到的内容：

- **营销活动**：列表、文件夹中的活动数量、每个已授权营销活动的设置、步骤、活动记录及其分析数据。活动记录使用经过安全处理的消息和指定的元数据；不会返回未授权邮箱的身份信息和详情、邮件服务商的原始错误信息或未知元数据。其他营销活动均返回“未找到”，通过直接链接访问也一样。
- **分析数据**：控制台和营销活动报表，计算范围仅限其获授权的营销活动与邮箱。筛选条件与授权范围取交集后，重新计算营销活动数量。
- **工作区概览**：营销活动数量只统计其获授权的活动；联系人数统计这些活动中的去重联系人；邮箱数量只统计其获授权的邮箱。今日已确认的营销活动发送量必须同时属于获授权的营销活动和获授权的邮箱。成员数量和 AI 语气相关字段不予显示。
- **收件箱**：其获授权邮箱中的会话，以及相应的数量统计和筛选选项。分类列表只包含已应用到含有可访问邮箱邮件的会话上的分类。访问会话标签要求该会话中至少有一封可访问的邮件；未知会话与无权访问的会话都返回“未找到”。
- **实时更新**：仅接收这些资源的更新。受限成员不会出现在团队在线状态中，也看不到其他人的在线情况。

尚无法按访问范围缩小权限的功能对这些成员不可用，侧边栏会显示锁定状态及原因：联系人、CRM、模板、表单、自动化流程、邮件送达能力、投递位置测试、个人资料和个人安全之外的设置、AI 助手以及 Slack 应用。资源所有权不能绕过实时事件或通知的访问检查。他们不会收到工作区通知，包括已经排队的邮件或推送通知；在成员身份受限或被移除期间，已存储的工作区通知也会隐藏。个人登录安全通知仍然可用。受限成员已有的 API 密钥以及其授权的应用，同样受该访问范围和只读路由限制；他们不能创建新密钥。

如果账户在所有工作区中的成员身份都受到访问范围限制，则无论当前选中哪个工作区，都不能创建其他工作区。没有任何成员身份，或至少在一个工作区中拥有不受限成员身份的账户，仍可在现有限额内创建工作区。实例管理员不受此限制。提交、查看列表或取消工作区限额申请，都要求用户在该申请所针对的工作区中拥有不受限的成员身份，仅在当前选中的工作区中不受限并不足够。这些规则同时适用于托管和自托管实例。

修改成员的访问范围需要**管理团队**权限，并且操作者近期完成过登录验证。变更会在成员下一次请求时生效，直接应用到其已打开的控制台和实时更新，无需重新加载。实时授权缓存最多保留 30 秒；重新检查拒绝访问或检查失败时，营销活动与邮箱通道会关闭。组织通道在收到相关变更事件时刷新授权，并使用同样具有时间上限的定时刷新机制。你必须拥有该成员角色授予的每一项权限；所有者始终可以访问整个工作区；你不能修改自己的访问范围。文件夹、营销活动或邮箱被删除后，其对应的授权也会一并消失。

现有不受限成员继续保有整个工作区的访问权限。这些保护措施使用现有成员授权，不需要新的配置或数据迁移。自托管运维人员应同时更新后端/消费者服务和实时服务，确保 API、通知和通道检查都运行更新后的代码。

## 角色 [#roles]

角色属于工作区数据。每个工作区最初都有三个预设角色，它们与普通角色完全相同：你可以重命名、更改颜色、修改权限或删除，也可以添加自己的角色。**所有者是一种成员身份，而非角色**，每个工作区恰好有一位所有者。

| 角色 | 初始权限 |
| --- | --- |
| **所有者**（身份） | 完全控制，包括转移所有权 |
| **管理员** | 除转移所有权之外的所有权限 |
| **运营者** | 日常运营权限：营销活动、联系人、邮箱、集成。没有团队、账单、设置或 API 密钥权限 |
| **查看者** | 只读 |

### 权限 [#permissions]

| 领域 | 权限 | 允许执行的操作 |
| --- | --- | --- |
| **数据** | 查看 / 管理营销活动 | 读取设置、邮件序列、分析数据 / 创建、编辑、归档 |
| | 查看 / 管理联系人 | 读取联系人、分群、标签 / 创建、编辑、删除 |
| | 管理邮件序列 | 编辑步骤内容和间隔 |
| | 查看分析数据 | 查看邮件送达能力和互动报表 |
| | 使用集成 | 将联系人和商机推送到已连接的工具，查看和测试自动化流程 |
| | 使用 AI | 使用 Remie 和 AI 撰写功能，消耗共享积分 |
| **人员** | 管理团队 | 邀请、移除成员，调整成员角色 |
| | 转移所有权 | 将所有权移交给另一位成员 |
| **发送** | 管理邮箱 | 连接、断开和配置发件邮箱 |
| | 发送营销活动 | 启动、暂停、恢复 |
| | 使用统一收件箱 | 从共享收件箱读取和回复邮件 |
| **工作区** | 管理设置 | 修改工作区级设置、连接集成、构建自动化流程 |
| | 管理账单 | 结账、查看发票、变更和取消套餐 |
| | 管理 API 密钥 | 创建和撤销工作区密钥 |

预设角色的权限分配如下：**查看者**只有两项查看权限以及分析数据权限。**运营者**在此基础上增加所有日常运营权限，包括管理营销活动、联系人、邮件序列和邮箱，以及发送、统一收件箱、集成和 AI。**管理员**再增加团队、设置、账单和 API 密钥权限。**所有者**拥有管理员的所有权限，并可转移所有权。

角色还限制成员可以向软件授予哪些权限。成员创建的 API 密钥以及通过 OAuth 授权的应用，只能获得[该成员角色涵盖的 API 权限](/api/permissions/#what-a-role-can-delegate)。如果之后修改成员的角色，应用的访问权限也会随之缩小。具有**管理 API 密钥**或**管理设置**权限的成员，可在**设置 > OAuth 应用 > 已授权的应用**中查看所有成员授权的应用，并撤销其中任何一个。

</Fold>

## 自定义角色 [#custom-roles]

在**角色与访问权限**页面点击**新建角色**：填写名称（最多 50 个字符，只有“owner”是保留名称）、颜色和可选的说明。在**以此为基础**中选择模板以复制一组权限，再逐项开启或关闭权限。创建后，可以从成员列表或邀请流程中进行分配。

以下五项规则确保权限管理的安全：

- **编辑角色会立即更新分配了该角色的所有成员。** 保存之前，编辑器会显示受影响的成员数量。
- **你只能授予或收回自己拥有的权限**，因此任何人都不能创建权限高于自身的角色。修改角色权限、删除角色、调整成员角色和移除成员，都要求操作者拥有变更前后涉及的全部权限；所有者拥有所有权限。
- **自定义角色绝不能包含转移所有权权限。**
- **成员可以拥有多个角色**，实际权限为这些角色权限的并集。如果成员不再拥有任何角色，其成员身份仍然保留，但没有任何权限。
- 每个工作区最多可以有 25 个角色，包括预设角色。

自定义角色适用于所有进行权限判断的地方：API 访问检查、控制台内容可见性，以及成员能够接收哪些实时事件。对于[访问范围](#access-scope)受限的成员，只有角色的读取权限生效。
